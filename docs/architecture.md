# Architecture Guide

Flasher uses a minimal, idiomatic Go architecture strictly isolating the User Interface from the Business Logic and external command executions. 

## Core Principles
1. **Separation of Concerns:** UI code (`tui`), business orchestration (`core`), and infrastructure/configuration (`config`) must never tightly couple.
2. **Context-Driven Execution:** All background operations must use `context.Context` to allow clean timeouts and user cancellations.
3. **Platform Independence:** Binary paths (ADB/Fastboot) are dynamically resolved checking embedded payloads, absolute paths, and the system `PATH`.

## Package Layout
- `cmd/flasher`: The application entry point and Cobra CLI commands (`root`, `flash`, `inspect`, `devices`, `version`).
- `internal/config`: Application configuration, structured logging initialization, and the central dependency injection `App` container. Provides strict environment variable and file validation upon load.
- `internal/core`: The business orchestration layer. Executes processes, tracks long-running commands, and hosts `FlashService` and `DeviceService`. Contains the robust `ValidationService` that enforces safety rules before any flash operation, and defines the explicit `FlashState` state machine.
- `internal/platform`: Low-level integrations. Contains device scanning logic, device state types, binary resolution, and embedded payloads. All system commands are wrapped with context propagation, timeouts, and intelligent retry logic.
- `internal/tui`: The Bubble Tea framework rendering the TUI. Managed in modular files (`model.go`, `view.go`, `update.go`, `handlers.go`). Views react natively to the `FlashState` engine instead of disparate boolean flags.

## Device Dashboards
The dashboard consumes the platform scanner's confirmed ADB/Fastboot state and the platform dashboard collectors/parsers. The TUI renders separate Android/ADB and concise Fastboot summary panels, plus explicit guidance for disconnected, unauthorized, offline, and ambiguous-device states. Fastboot shows device identity/connection, bootloader security and battery status, and a short allowlist of key variables; it omits the full partition inventory and flash-preparation panel. Ambiguous scans preserve the candidate list and require the operator to select a target before actions can run.

Dashboard collection is read-only and uses bounded command timeouts. Missing properties remain unknown, sensitive diagnostic values are redacted, and collection errors do not discard partial results. ROM compatibility is evaluated in `internal/core/compatibility.go`; no device-specific compatibility profiles are hardcoded. The dashboard displays the evaluator's report for the selected package and target. ZIP inspection reads only selected metadata entries, applies entry-count/decompression limits, rejects unsafe paths, and never executes installation scripts. Recognized target declarations include Android OTA `pre-device`, simple updater-script device assertions, and `META-INF/flasher/compatibility.json`. Package metadata is untrusted. A verified target mismatch, malformed package, or conflicting metadata blocks. If compatibility is unknown or only a candidate match, a user must explicitly confirm the warning before flash, wipe-super, or sideload; this is not a `VERIFIED` result. Raw boot images have no reliable target identity and require the same explicit unverified-compatibility confirmation.

The connected device identity is read from ADB/Fastboot discovery; display-name mappings are informational and do not authorize operations. `CompatibilityEvaluator` is injectable for integrations with independently reviewed evidence; callers must not promote package-authored declarations to trusted evidence. The TUI and CLI rely on core validation at execution, and the TUI dashboard reports the same compatibility state.

`core.InspectROM` and the `inspect` CLI command provide a read-only JSON report for package format, archive entry/compressed/uncompressed sizes, declared target IDs, partition names, discoverable firmware requirements, payload manifest metadata, and SHA-256. The inspector reads package metadata and a bounded Android OTA `payload.bin` v2 manifest; it never extracts images or executes installation scripts. Limits are 32 GiB per package, 10,000 ZIP entries, 2 MiB per recognized metadata entry, 8 MiB combined recognized metadata, 16 MiB per payload manifest, and 4,096 payload partition records. Unsafe paths, symlinks, malformed ZIP metadata, and malformed payload manifests are surfaced rather than trusted. Metadata declarations remain untrusted, and payload partition names are informational rather than proof of compatibility requirements.

The report keeps integrity separate from compatibility. Its SHA-256 state is `CALCULATED_ONLY` unless a caller supplies an independently sourced expected checksum, in which case it reports `EXPECTED_MATCH` or `EXPECTED_MISMATCH`; even a match is not authenticity or compatibility evidence. A supplied checksum is verified again in the core execution path; a mismatch blocks. Verified compatibility requires independent evidence, including the requested partition. Unknown or candidate compatibility can proceed only with explicit risk acknowledgement and a warning; target conflicts and malformed input still block. `--force` applies only to the battery override and does not bypass those blockers.

All device-changing commands dispatched through `Engine.RunCommand` require a private, exact-command authorization created only by a core operation after validation. Unrecognized, normal-risk, and dangerous commands are rejected when submitted directly, including via custom-command entry. `FlashService` operations require explicit risk acknowledgement (`--yes` in the CLI or the existing TUI confirmation); legacy write methods without acknowledgement fail closed. Targeted flash, wipe-super, and sideload calls pin and recheck the selected serial. Battery, bootloader, package, compatibility, partition, expected-hash (when supplied), and acknowledgement decisions are enforced by core services, not only by UI preflight.

`flasher flash <partition> <image> --dry-run` runs read-only device identification and core planning, prints the exact target/operation/file, checksum and compatibility state, and every blocker, then exits without calling the write executor. The dry run treats risk acknowledgement as satisfied only for displaying the plan and never sends the operation. For an actual CLI flash, `--yes` is required; unknown/candidate compatibility additionally requires `--allow-unverified-compatibility`.

Device-changing application entry points are: CLI `flash`; TUI Flash Boot/Recovery, Wipe Super, Sideload, Reboot System/Recovery; and core Fastboot flash/wipe-super, ADB sideload, and device reboot services. The TUI custom-command flow accepts classified read-only commands and, without a confirmation prompt, explicit reboot requests plus the exact Fastboot commands `reboot bootloader`, `reboot-bootloader`, `reboot fastboot`, `reboot recovery`, and `set_active a|b`. These Fastboot requests are rechecked against the selected device before dispatch. Other device-changing custom commands remain blocked. `Engine.RunCommand` rejects all other command classes unless the exact command was authorized by a core service. Platform scanners issue only device-list, getvar, getprop, and battery diagnostic queries.

No new dependency is used for inspection. `archive/zip` and `crypto/sha256` are sufficient for archive reading and hashing. The reviewed [`github.com/ssut/payload-dumper-go`](https://github.com/ssut/payload-dumper-go) release is actively maintained (latest release 2.1.0, September 2026) under [Apache-2.0](https://github.com/ssut/payload-dumper-go/blob/main/LICENSE) and exposes manifest/partition metadata. Its [module file](https://github.com/ssut/payload-dumper-go/blob/main/go.mod) currently requires Go 1.27, above this project's Go 1.25.6 minimum, and adds a larger decompression/progress dependency tree. The `NewFromReaderAt` API allocates a manifest buffer directly from the untrusted header length without an application-level cap. Although the project publishes Windows binaries, its source README describes a CGO-based XZ decompression path; a Windows library build would need a compatible C toolchain and separate verification. A local bounded parser avoids those compatibility/resource costs. It currently supports payload header major version 2 only.

Fastboot unlock state is distinct from secure-boot state; flashing requires an explicit unlocked response. Flash, sideload, and reboot operations revalidate and pin the selected serial. Custom commands accept recognized read-only operations without a prompt, plus exact reboot requests (`reboot`, `reboot system`, `reboot recovery`) and the explicit Fastboot commands documented above. Before dispatch, the TUI refreshes and compares the selected device. All other mutating custom commands remain rejected.

## Concurrency & Safety
Concurrency is restricted to prevent device corruption. The `core.Engine` tracks the active command cancellation context, while scanner and dashboard collection use bounded execution and generation checks to discard stale UI results.

TUI rendering performance is protected by asynchronous commands and periodic log updates so device operations do not block the main Bubble Tea loop. See [hardware-validation.md](hardware-validation.md) before testing on physical devices.

If a device-changing process is canceled, times out, or exits with an error after it starts, the engine returns `ErrOperationIndeterminate`; this is distinct from a completed command failure because the device may have received no data, partial data, or the complete transfer. A process error is not treated as proof that the device was unchanged. The TUI marks device state as unknown, starts a fresh scan, and blocks subsequent flash, wipe, sideload, and reboot actions. Read-only diagnostics and refresh remain available. The gate clears only after a fresh scan (or an explicit fresh candidate selection) finds the same serial in a definite device mode. A missing, different, disconnected, offline, or ambiguous result leaves the gate in place.

Reconciliation only rereads current connection/device state; it cannot establish whether a transfer completed, validate all partition contents, or undo changes. Operators must inspect the device and package using an appropriate device-specific recovery procedure before deciding what to do next. A new action still passes the usual core validation and acknowledgement checks after the TUI gate clears.

The TUI calculates a separate content fingerprint asynchronously after a file is selected; CLI flash preflight calculates one before planning. This calculated SHA-256 fingerprint binds later confirmation/preflight to the selected bytes, and is not the caller-supplied `ExpectedSHA256`. A fingerprint is only a content identity check: it does not prove source, publisher, authenticity, or compatibility. The selection-time fingerprint is recomputed from actual file bytes before confirmation and execution.

Before Fastboot flash, wipe-super, or ADB sideload, core copies the selected input into a uniquely named private temporary directory, hashes the copied bytes, and rejects the operation if they differ from the bound fingerprint. It evaluates compatibility and any supplied expected checksum against that snapshot, then gives platform-tools the snapshot path, not the original path. The directory and file are created with restrictive 0700/0600 permissions where supported (on Windows, access inherits from the OS temporary directory's ACL); the file is closed before process launch and both are explicitly removed when the operation returns. This prevents later replacement of the selected source path from changing bytes consumed by platform-tools. The configured operating-system temporary directory must have enough free space for another full copy of the image/package; staging can temporarily require approximately the source file's size in addition to the original. An abrupt process termination may leave a snapshot behind for manual cleanup.

`ExpectedSHA256` remains a separate optional comparison against a checksum supplied by the caller; a match is not authenticity evidence unless that expected value was obtained and trusted independently. A calculated fingerprint—even when displayed as a full SHA-256 value—does not confer trust.

The core exposes side-effect-free plans for Fastboot flash, wipe-super, ADB sideload, and system/recovery reboot. Planning does not invoke the transport. The CLI `--dry-run` flag is currently exposed for `flasher flash`; the TUI does not expose a dry-run action for its wipe, sideload, or reboot menu entries. Those actions remain subject to core authorization and validation.
